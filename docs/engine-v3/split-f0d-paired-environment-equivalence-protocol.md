# Split F0D paired environment equivalence protocol

Version: `stayopti.split-f0d.equivalence-protocol@1`

Status: private, provider-neutral dry-run contract. It is not V3-19, market evidence, policy, ranking, a public recommendation, or authorization to call a provider.

## Purpose and claim boundary

This protocol prepares an exact paired comparison of LiteAPI sandbox and production while keeping engine behavior separate from provider data. Source-code identity, request identity and deterministic replay can be proved offline. Inventory, availability, prices, taxes, rate plans and search-level bookability remain environment-dependent until a separately authorized production read-only run.

CI success and identical source code do not prove sandbox/production data equivalence. Prices from the two environments are never treated as observations from the same market and are never subtracted from each other.

V2 remains the public authority. V3 remains OFF/shadow. Public Split remains disabled. No result produced by this protocol may enter policy, ranking, a public boundary, booking, payment or a user-facing claim.

## Frozen live matrix

The only live scenario source is `tests/engine-v3/fixtures/split-f0-scenario-matrix-v1.json`. The paired run plan references its eight scenario IDs and does not copy destination, date or occupancy data.

The live durations remain exactly 5, 7, 10, 12, 14, 21, 28 and 30 nights. Every scenario has one full-stay search and two pairs of segment searches, for five logical searches. The 21-night case remains present because it carried the only stable primary sandbox signal. The 28- and 30-night cases remain present because production availability is unknown.

The two-night case is offline-only. It proves that a full-stay period can exist while no split point can produce two segments of at least two nights. It plans zero provider requests.

Four additional provider-neutral replay controls cover:

1. no gross-saving Split;
2. an economically positive Split candidate;
3. essential evidence missing and fail-closed comparability;
4. loss of availability that changes the fixed best single.

These controls are diagnostics, not provider observations.

## Paired schedule

There are two environments (`sandbox`, `production`) and two waves (`wave-a`, `wave-b`). Each wave contains 40 request pairs. Every pair contains the same logical request for both environments.

- In wave A, even pair ordinals run sandbox then production; odd ordinals run production then sandbox.
- In wave B, that order is reversed.
- Requests are executed pair-by-pair. Running all sandbox requests before production, or vice versa, is prohibited.

The future live plan therefore contains:

`8 scenarios x 5 searches x 2 environments x 2 waves = 160 HTTP requests`

Dry-run remains the default and must report zero actual HTTP requests. D.3 adds
an explicitly gated live mode without changing the dry-run schedule or hashes.

## Request identity

Every pair is bound to the exact request body generated by the existing F0C request-body builder. The canonical receipt contains only scenario ID, wave ID, logical search ID, stay duration, dates, occupancy, currency, nationality, search kind, split point, non-secret request configuration and the SHA-256 of the canonical body.

Environment label, base URL, credentials, headers and operational timestamps are excluded from the body hash. Sandbox and production hashes for the same pair must be identical. One mismatch invalidates the complete dry-run.

## D.3 live gates

Live execution is reachable only when both
`--execute-paired-live` and
`--confirm-rates-only-production-access` are present. Missing either flag stops
before environment or transport access. The runner accepts credential variable
names, never credential values, and uses these process bindings:

- sandbox base URL;
- production base URL;
- sandbox credential with `sand_` class;
- production credential with `prod_` class.

There is no fallback between environments. Missing or wrongly classified production credentials produce `PRODUCTION_CREDENTIAL_CLASS_NOT_PROVEN` before network access. Credential values must never be printed, hashed, persisted or passed on the command line.

The future transport must enforce:

- HTTPS and the explicit `api.liteapi.travel` host allowlist;
- `POST /hotels/rates` as the only endpoint;
- native Node 24 `fetch` with `redirect: "error"` and every redirect rejected;
- concurrency 1 and at most one request per second;
- retry 0, cache disabled and `continuation=none`;
- a hard budget of 160 requests;
- immediate stop when truncation or continuation is reported;
- zero Prebook, Book, cancellation, payment, wallet, checkout, commission or markup endpoints.

The response gate accepts only HTTP 200 JSON from the same HTTPS host. Invalid
JSON, non-JSON content, an uninterpretable rates schema, or any continuation or
truncation signal stops the run. A 401/403 or 429 stops globally. Timeout and
5xx make the current pair inconclusive with retry zero; no replacement request
or cross-environment fallback is allowed.

The 160-request schedule is executed pair-by-pair with concurrency one. A
single ephemeral HMAC-SHA256 key correlates provider identifiers in memory
across both environments and waves. Only HMAC fingerprints may enter the
sanitized output, and the key itself is never persisted.

## Privacy

Persisted receipts exclude credentials, headers, cookies, tokens, raw property/room/rate/offer identifiers, commercial URLs, names, addresses and PII. A future live run may correlate identifiers only with HMAC-SHA256 using one ephemeral in-memory key shared by both waves and never written to disk.

## Comparison semantics

Each environment and wave is evaluated independently for availability, field coverage, strict/conditional comparability, fixed best single, best compatible Split, primary gross saving, friction sensitivity, outliers and instability.

The comparator invariants remain:

- choose one fixed best single before inspecting Split pairs;
- reuse that baseline for both split points in the same scenario/environment/wave;
- calculate money in integer EUR minor units with no unsupported precision;
- keep matched-bucket diagnostics outside the headline;
- quarantine outliers from robust metrics without deleting observations;
- produce no public recommendation.

Cross-environment output may describe schema, coverage, behavior, availability and economic-signal direction. It must not assert equal prices, equal inventory, market savings, production bookability or recommendation eligibility.

## Outcome contract for the later live phase

`PASS` requires identical canonical requests, the same engine artifact, deterministic replay for equal normalized inputs, preserved fixed-baseline and quarantine gates, complete safety receipts and every observed divergence classified as configuration, provider data or operations.

`FAIL` includes unapproved request/config drift, divergent engine output for identical normalized input, split-conditioned baseline selection, monetary error, prohibited endpoint, secret/raw-ID persistence, or any booking/payment action.

`INCONCLUSIVE` includes missing production access, 401/403, 429, timeout, partial/truncated response, essential schema absence, incomplete pairs or timing volatility that prevents attribution.
